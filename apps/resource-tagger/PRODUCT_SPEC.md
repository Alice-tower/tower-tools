# 本地资源语义管理器｜产品与实现方案 v0.2

> 历史方案：2.0.0 的存储与扫描规则以 [Bucket 与 NAS](BUCKET_STORAGE.md) 为准；预览扩展以 [预览架构](PREVIEW_ARCHITECTURE.md) 为准。本文保留原始需求，不代表当前目录层级。

## 1. 产品定位

这是一个建立在本地文件系统之上的**资源语义管理与导航工具**。

系统以用户指定的 Root 目录为扫描入口，将 Root 下直接包含的目录和文件作为受管理资源，通过 Tag 建立语义组织、筛选和关联能力。

产品主要回答：

- 我有哪些相关资源？
- 哪些资源属于同一主题？
- 如何快速找到符合多个条件的一组资源？
- 如何快速定位这些资源在文件系统中的位置？

产品可以理解为：

**文件系统之上的展示层、语义层和导航层。**

系统不复制、搬移或接管文件，不替代资源管理器，也不建立全盘文件索引。

## 2. 本版相对 v0.1 的变化

1. 将核心实体 `Directory` 泛化为 `Resource`。
2. Resource 同时支持目录和单个文件，通过 `kind` 字段区分。
3. Root 扫描固定为一层，只发现直接子项，不递归进入子目录。
4. 移除 `scan_depth` 配置。
5. 目录和文件共用 Tag、筛选、状态和 Review Queue。
6. 不建立资源父子关系，不提供标签继承。
7. 目录提供“打开目录”和“在所在目录中显示”；文件只提供“在所在目录中显示”。
8. 内置媒体 Viewer 留作后续扩展，不属于第一版交付范围。

## 3. 核心原则

### 3.1 只扫描 Root 的直接子项

例如：

```text
D:\Resources\             ← Root，不作为资源入库
├─ 游戏A\                ← 发现为目录资源
│  └─ 攻略.pdf           ← 不扫描、不入库
├─ 图片集\               ← 发现为目录资源
└─ 说明.pdf              ← 发现为文件资源
```

不读取子目录内容，不为目录内部文件建立记录。

### 3.2 数据库只保存语义和定位信息

文件系统保存实际内容；数据库保存：

- Root 配置；
- 资源身份及位置；
- 资源状态；
- Tag 及别名；
- 资源与 Tag 的关系；
- 扫描后需要用户处理的事项。

移除数据库记录不得删除实际文件或目录。

### 3.3 稳定 ID 与路径分离

Root、Resource、Tag 都使用稳定 ID。

Resource 不使用绝对路径作为主键。Tag 不使用名称作为主键。

### 3.4 标签是主要交互对象

UI 重点是：

- 为资源添加和移除 Tag；
- 搜索 Tag 及别名；
- 通过多个 Tag 筛选资源；
- 从结果定位实际目录或文件。

第一版不扩展为文件管理器、媒体数据库或知识图谱。

## 4. 核心实体

核心语义实体为 `Resource` 和 `Tag`，Root 是扫描及定位配置实体。

### 4.1 Resource

代表一个 Root 下直接包含的目录或文件。

建议字段：

```text
id
root_id
relative_path
kind              directory / file
display_name
status            Active / Missing / Ignored
created_at
last_seen_at
```

规则：

- `id` 是稳定身份。
- `relative_path` 保存相对 Root 的路径；本版仅允许直接子项。
- `kind` 是系统属性，不是 Tag。
- `display_name` 默认使用文件或目录名称。
- 文件显示名默认保留扩展名。
- 第一版不提供独立显示名编辑，重新定位后同步名称。
- 不记录目录内部资源清单。
- 不要求记录文件哈希、媒体信息或内容全文。

关系：

```text
Root → Resource ←→ Tag
```

### 4.2 Tag

Tag 表示一个语义概念，拥有稳定 ID。

例如：

```text
id: 42
canonical_name: Cyberpunk

aliases:
赛博朋克
cyber punk
サイバーパンク
```

资源关联始终绑定 `tag_id`。修改 Tag 名称或别名不得破坏现有资源关联。

一个资源可以拥有多个 Tag，一个 Tag 可以关联多个资源。

### 4.3 不建立资源层级关系

目录资源和文件资源平等参与管理。

不提供：

- Resource 父子关系；
- 目录标签向文件继承；
- 子项标签向目录汇总；
- 因目录入库而自动管理内部文件。

## 5. Root 管理

Root 是用户主动添加的扫描目录。

例如：

```text
D:\Games
D:\Images
E:\Documents
```

Root 管理需要支持：

- 添加 Root；
- 编辑显示名称；
- 手动扫描；
- 修改 Root 路径，即重新定位 Root；
- 查看扫描状态和最近成功扫描时间；
- 移除 Root。

规则：

1. Root 必须是目录。
2. Root 本身不作为 Resource 入库。
3. 不扫描整块磁盘或未配置的路径。
4. 同一个实际规范化路径不得重复添加。
5. 第一版不允许 Root 相互嵌套，避免同一区域形成多重管理入口。
6. 第一版只提供手动扫描，不要求定时扫描或文件系统实时监听。
7. Root 暂时不可访问时保留配置和资源数据。

移除 Root 会同时移除其数据库资源记录和标签关联，但保留 Tag 定义及磁盘内容。UI 必须明确说明并要求确认。

## 6. 扫描行为

### 6.1 扫描范围

扫描 Root 的直接文件和直接目录，不递归。

第一版：

- 不按扩展名过滤普通文件；
- 不自动解析文件内容；
- 默认跳过具有 Hidden 或 System 属性的子项；
- 默认跳过符号链接、目录联接等重解析点；
- 暂不提供复杂扫描规则编辑器。

以上过滤规则是第一版默认实现策略。

### 6.2 扫描结果

比较当前成功扫描结果和数据库记录，得到：

```text
Added
Missing
Unchanged
```

另外识别：

- 已缺失资源重新出现；
- 同一路径的类型发生变化。

只有完整、成功的扫描才能用于判定 Missing。

Root 不存在、离线、无权限或扫描中途失败时：

- 标记 Root 扫描失败或不可访问；
- 展示可理解的错误；
- 不把其资源批量标记为 Missing；
- 不将不完整结果当成一次成功扫描提交。

### 6.3 新发现资源

成功扫描后为新资源建立稳定记录，并生成 New 待处理项。

新资源可以没有 Tag。

Review Queue 中可执行：

- 添加 Tag；
- 确认收录，即使暂时没有 Tag；
- 忽略；
- 执行与资源类型对应的导航操作。

New 是“待处理状态”，与资源是否存在的状态分开保存。

### 6.4 缺失资源

此前存在、本次成功扫描未发现的资源标记为 Missing，并进入待处理队列。

必须保留：

- Resource ID；
- 原路径；
- 已有 Tag；
- 创建时间等记录。

用户可以：

- 保留记录并确认本次提醒；
- 重新定位；
- 从数据库移除。

已经确认保留的 Missing 资源，在后续仍然缺失时不重复生成相同提醒。若恢复后再次缺失，可以重新提醒。

### 6.5 忽略资源

Ignored 表示用户不希望该资源出现在日常管理结果和待处理列表中。

规则：

- 普通结果默认隐藏 Ignored；
- 后续扫描不重复提示同一个被忽略项；
- 提供查看和取消忽略的入口；
- 忽略不删除实际内容；
- 取消忽略后重新检查存在情况，恢复为 Active 或 Missing。

### 6.6 资源恢复与类型变化

原路径再次出现、类型一致时，可以将 Missing 恢复为 Active，并保留 ID 和 Tag。

同一路径由文件变为目录，或由目录变为文件时，进入 Review Queue，要求用户确认是否将原记录关联到当前对象。不得静默将旧 Tag 转移给不同类型对象。

第一版不通过哈希或文件系统对象 ID 识别内容身份。相同路径、相同类型的替换，不保证自动识别。

## 7. 资源身份与重新定位

保存：

```text
root_id
relative_path
```

实际路径通过 Root 路径与相对路径组合得到。

例如：

```text
Root:
D:\Resources

Resource:
说明.pdf
```

Root 从 `D:\Resources` 改为 `E:\Resources` 时，仅更新 Root 路径，保留资源 ID、相对路径及标签关系。

### 7.1 资源移动或改名

第一版不自动猜测移动或改名关系。

扫描可以先发现：

```text
旧路径 Missing
新路径 Added
```

用户通过“重新定位”将旧记录关联到新位置，保留原 ID 和 Tag。

目标必须：

- 位于已配置 Root 下；
- 是该 Root 的直接子项；
- 与原资源类型一致。

若目标已对应一个未处理、无标签的新发现记录，可以明确提示用户后合并，保留旧记录。

若目标已是独立管理且带有语义数据的资源，阻止自动合并并提示冲突，第一版不实现复杂合并流程。

### 7.2 路径比较

集中实现路径规范化，避免扫描、入库和重新定位各自使用不同规则。

至少处理：

- 绝对路径规范化；
- 路径分隔符；
- 多余末尾分隔符；
- Windows 常规大小写不敏感比较；
- 路径不能通过 `..` 逃离 Root；
- 保留原始名称用于显示。

第一版面向常规 Windows 文件系统使用场景；遇到无法可靠区分的路径冲突应明确报错，不静默覆盖记录。

## 8. Tag 与 Alias

### 8.1 Tag 操作

第一版支持：

- 创建 Tag；
- 修改规范名称；
- 删除 Tag；
- 添加及删除 Alias；
- 给单个或多个资源添加、移除 Tag。

删除 Tag 时，删除其别名及资源关联，不影响资源记录或实际文件。操作前显示关联资源数量并确认。

### 8.2 Alias 的用途

Alias 用于：

- 搜索；
- 自动补全；
- 多语言名称匹配；
- 用户习惯名称匹配。

Alias 与规范名称指向同一个 Tag ID，不创建多个重复 Tag。

第一版统一显示规范名称，不根据别名自动切换 UI 语言。

### 8.3 名称约束

第一版采用全局唯一的 Tag 名称空间，不引入 namespace UI。

对规范名称和 Alias：

- 去掉首尾空白；
- 不允许空字符串；
- 使用一致的 Unicode 规范化及大小写不敏感匹配规则；
- 不同 Tag 不能占用同一个规范化名称或别名；
- 同一 Tag 内也不重复保存相同名称。

发生冲突时提示已有 Tag，允许直接使用已有 Tag。

## 9. Tag 筛选

Tag 支持三态：

```text
Neutral
Include
Exclude
```

第一版查询语义：

- 所有 Include Tag 必须同时满足；
- 任意 Exclude Tag 命中则排除；
- Neutral 不参与查询。

例如：

```text
+ game
+ fromsoftware
- completed
```

表示：

```text
包含 game
并且包含 fromsoftware
并且不包含 completed
```

第一版不支持 OR 或嵌套表达式。

交互要求：

- Include、Exclude 的状态清楚可辨；
- 提供直接切换状态的操作；
- 提供清空筛选；
- 搜索规范名称及 Alias 时都能找到对应 Tag；
- 同一个 Tag 不得同时进入 Include 和 Exclude。

资源列表额外支持：

- 名称搜索；
- Root 筛选；
- 类型筛选：全部、目录、文件；
- 状态筛选；
- 无标签资源筛选。

文本搜索匹配资源显示名及相对路径，不搜索文件内容。

## 10. 资源展示与右键操作

资源列表至少展示：

- 名称；
- 类型图标；
- 所属 Root；
- Tag；
- 状态。

详情区域展示实际路径及完整标签。

### 10.1 目录资源

右键提供：

```text
打开目录
在所在目录中显示
编辑标签
忽略
从数据库移除
```

- “打开目录”：在资源管理器中进入该目录。
- “在所在目录中显示”：打开父目录并选中该目录。

### 10.2 文件资源

右键提供：

```text
在所在目录中显示
编辑标签
忽略
从数据库移除
```

第一版不提供文件直接打开、默认应用启动或内置预览。

### 10.3 不可用资源

Missing 资源提供：

```text
重新定位
保留记录
编辑标签
从数据库移除
```

依赖对象实际存在的导航操作应禁用或给出明确提示。

Root 不可访问时同样需要提示，不应仅根据历史 Active 状态假定资源仍可打开。

### 10.4 其他交互

- 双击不引入右键菜单之外的额外行为。
- 第一版可采用单击选中、详情查看、显式导航按钮。
- 导航参数必须正确处理中文、空格及特殊字符。
- “从数据库移除”明确表示仅移除记录。
- 对仍存在的资源，移除记录后下次扫描会重新发现；希望长期隐藏应使用“忽略”。

## 11. 主界面

建议采用三块布局：

### 左侧：范围和标签筛选

- 全部资源；
- Root 列表；
- Review Queue 入口及数量；
- 类型及状态筛选；
- Tag 搜索与三态筛选。

### 中间：资源结果

- 名称搜索；
- 当前筛选条件；
- 资源列表；
- 多选及批量标签操作；
- 结果数量。

### 右侧：资源详情

- 名称和类型；
- 所属 Root；
- 实际路径；
- 状态；
- Tag 编辑；
- 对应导航操作。

Root 管理、Tag 管理和 Review Queue 可以使用独立页面或对话框，不要求固定为某一种布局。

UI 至少包含：

- 空数据库引导；
- 无匹配结果；
- 扫描进行中；
- Root 不可访问；
- 操作失败反馈。

扫描在后台执行，不阻塞 Compose UI。同一 Root 不允许并发扫描。

## 12. SQLite 数据结构方向

以下是逻辑模型，执行 Agent 可细化物理结构，但不得改变产品行为。

### roots

```text
id
path
normalized_path
display_name
availability_status
created_at
last_scan_at
last_successful_scan_at
last_scan_error
```

### resources

```text
id
root_id
relative_path
normalized_relative_path
kind
display_name
status
created_at
last_seen_at
```

### tags

```text
id
canonical_name
created_at
```

### tag_names

推荐统一保存规范名称和别名的可搜索索引，以便落实跨名称类型的唯一约束：

```text
id
tag_id
name
normalized_name
name_kind           canonical / alias
```

`canonical_name` 与对应名称记录必须事务性同步。也可以采用无重复存储的等效结构。

### resource_tags

```text
resource_id
tag_id
```

### review_items

```text
id
resource_id
reason              New / Missing / TypeChanged
state               Pending / Resolved
detected_at
resolved_at
```

可按需要增加当前观察类型等字段。

约束和索引至少包括：

- Root 规范化路径唯一；
- Resource 的 `(root_id, normalized_relative_path)` 唯一；
- Tag 的规范化名称及别名全局唯一；
- `(resource_id, tag_id)` 唯一；
- 外键约束；
- 按 Root、资源状态、Tag 关系和待处理状态查询所需的索引；
- 同一资源同一原因不重复生成待处理项。

扫描结果、状态变化及 Review Queue 更新应事务性提交。

删除 Resource 时清理关联及待处理项；删除 Root 时清理所属 Resource。所有删除均不得触及实际资源内容。

数据库结构需要带版本号，并提供后续迁移机制。

## 13. 模块划分

```text
Root Management
Scanner
Resource Registry
Tag System
Review Queue
Navigator
Desktop UI
```

职责：

- **Root Management**：管理扫描入口及可用性。
- **Scanner**：读取直接子项并生成差异。
- **Resource Registry**：维护稳定身份、路径和状态。
- **Tag System**：维护 Tag、Alias、关联及查询。
- **Review Queue**：处理新增、缺失及类型变化。
- **Navigator**：封装 Windows 资源管理器导航。
- **Desktop UI**：提供资源列表、筛选及管理流程。

文件系统访问、数据库和 UI 应适当分层，便于测试扫描差异和筛选逻辑；不需要为了扩展性建立复杂框架。

## 14. 第一版交付范围

必须完成：

1. Windows GUI 应用。
2. Root 添加、编辑、重新定位及移除。
3. Root 直接子项扫描，同时发现目录和文件。
4. SQLite 持久化。
5. Resource 稳定身份及状态管理。
6. New、Missing、TypeChanged Review Queue。
7. 忽略及取消忽略。
8. 资源重新定位。
9. Tag 创建、改名、删除。
10. Alias 管理及搜索匹配。
11. 单个与批量资源标签编辑。
12. AND / NOT 标签筛选。
13. 名称、Root、类型、状态和无标签筛选。
14. 约定的资源管理器导航操作。
15. 扫描失败反馈和用户数据保护。
16. 仓库启动器接入及 Windows 便携构建。

不纳入第一版：

- 递归扫描；
- 手动添加 Root 范围外的单个资源；
- 实时监听或定时扫描；
- 内容全文索引；
- 文件哈希及自动移动识别；
- 自动标签和 AI 分类；
- 标签继承；
- Tag-to-Tag 关系；
- OR 及嵌套查询；
- 图片、视频、音频 Viewer；
- 文件直接打开；
- 文件复制、移动、删除、改名；
- 云同步或多人协作。

## 15. 仓库与实现约束

执行前必须读取仓库实际 `AGENTS.md`，并遵守其中的最新规则。

当前明确要求：

- 每个工具必须提供 GUI。

## 16. 验收场景

### 16.1 扫描边界

给定：

```text
Root/
├─ A/
│  └─ inner.txt
└─ B.txt
```

扫描后仅发现 `A` 和 `B.txt`。Root 本身及 `inner.txt` 不入库。

### 16.2 统一标签

目录 A 与文件 B.txt 可以关联同一个 Tag，并同时出现在该 Tag 的筛选结果中。

### 16.3 组合筛选

包含两个 Include Tag、且不含任何 Exclude Tag 的资源才出现在结果中。

### 16.4 Alias

用别名搜索能找到规范 Tag；通过别名添加标签后，仅产生一条指向该 Tag ID 的关联。

### 16.5 缺失保护

移走 B.txt 后成功扫描：

- B.txt 标记 Missing；
- ID 和 Tag 保留；
- 出现待处理项；
- 不删除任何实际文件。

### 16.6 Root 离线

Root 不可访问或扫描失败时，不将已有资源批量标记 Missing。

### 16.7 重新定位

将缺失资源关联到合法新位置后：

- ID 不变；
- Tag 不变；
- 路径更新；
- 状态恢复；
- 不残留重复新发现记录。

### 16.8 忽略

忽略资源后，普通列表隐藏它，后续扫描不重复提醒；取消忽略后可以恢复管理。

### 16.9 导航

- 目录可以进入自身，或在父目录中被选中。
- 文件只支持在所在目录中被选中。
- 中文、空格及特殊字符路径正常工作。

### 16.10 持久化与构建

重启软件后配置和标签保留；重新构建便携包不影响已有用户数据。

## 17. 执行要求

执行 Agent 应以本方案完成第一版，不擅自扩展到递归索引、媒体浏览或文件操作。

优先打通完整流程：

```text
添加 Root
→ 扫描直接子项
→ 处理新发现资源
→ 添加 Tag
→ 标签筛选
→ 在资源管理器中定位
```

随后补齐 Missing、重新定位、忽略、错误处理和批量操作。

验证重点放在扫描边界、失败扫描不误判缺失、身份与标签保留、筛选正确性、名称冲突和数据库删除边界。

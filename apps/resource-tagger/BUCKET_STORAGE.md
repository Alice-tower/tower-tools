# Bucket 存储规则与 NAS 访问边界

当前版本：2.1.1，2026-09-22。以简单、少状态、完整保留功能为优先。规则是工作基线，可以随实际使用优化，不为尚未出现的需求建立复杂系统。

## 当前实现

```text
Root/
  bucket-000001/
    漫画 A/          # 一个目录资源；不扫描其内部
    视频 B.mp4       # 一个文件资源
  bucket-000003/
    漫画 A/          # 同名但路径不同，是另一个资源
  loose.txt          # 不登记
  other/             # 不扫描
```

- Bucket 名称为 `bucket-` 加六位数字，范围 000001–999999；Windows 大小写不敏感，允许断号。名称不匹配的 Root 子项仅在 Root 枚举时经过，不逐项读取属性或进入目录。
- 没有 Bucket 表或 Bucket ID，没有计数缓存、历史最大序号、自动整理或搬迁。Resource 仍直接关联 Root，保存 `bucket-000001/资源名称` 相对路径。
- 显示名称仍为最后一级名称；搜索同时支持显示名称和完整相对路径。路径唯一性按 Root 加完整相对路径判断，因此不同 Bucket 的同名资源不冲突。
- 目录资源无论内部文件多少都算一个。建议每个 Bucket 约 100 项；100 不是扫描或数据库限制，超出照常完整登记。
- 只登记 Bucket 的直接文件和目录，不读取文件内容，不深入资源目录。隐藏、系统、符号链接、联接及其他重解析对象继续排除。
- 重新定位可以在合法 Bucket 之间进行，保留资源 ID、标签及创建时间。不能重新定位到 Root 散放文件、非 Bucket 目录或资源内部后代。
- 插件和资源管理器导航统一使用宿主路径解析，不需要插件自己拼接 Bucket 路径。

## 失败与缺失

一次扫描完整枚举 Root 和全部合法 Bucket，成功后才事务性更新数据库。任何被扫描目录枚举或属性读取失败，整次结果不提交；仅更新 Root 的失败信息和尝试时间，保留资源、标签、待处理项及最近成功时间。

Root 成功枚举后，某个 Bucket 明确不存在（或被改为不符合规则的名称），其原有资源会进入 Missing；Bucket 恢复且资源路径/类型相同，保留身份和标签并恢复 Active。无法读取与明确消失不能混为一谈。

目前采用整 Root 的原子提交，未实现各 Bucket 独立提交或增量时间戳判断。文件系统持续被外部修改时，扫描不是文件系统快照；读取中发现异常会失败保留旧记录，可以稍后重试。

## 面向 SMB/NAS 的访问方式

数据库和日志继续存放本机 `%LOCALAPPDATA%/Alice-tower/TowerTools/dev.towertools.resourcetagger/`，不放到共享目录。

- 启动、筛选、分页、统计和标签写入只使用本地数据库，不自动扫描 NAS；离线仍可查看历史记录。
- 添加/重新定位 Root、用户手动扫描、导航及实际内容预览才访问资源路径。添加 Root 时需要网络可用。
- 完整扫描只枚举一次 Root，再各枚举一次合法 Bucket。读取子项时使用一份 DOS 属性获取类型、隐藏/系统等信息，不单独重复请求基本属性。普通文件不再额外调用 `toRealPath`；Root、Bucket 和目录资源仍保留规范路径检查，以排除目录重定向。
- 这些是 Java 层的调用边界，不等同于精确 SMB 请求次数；系统目录缓存、NAS 实现及网络延迟仍会影响速度。完整扫描仍随资源总数增长，不能承诺分组后快 100 倍。
- 预览继续按可见项请求，共享有限并发队列。当前标准插件无内容解码；缩略图磁盘缓存留到具体插件实现，没有虚构已存在的缓存能力。
- 不使用后台文件监听、定时轮询、目录时间戳跳过扫描或自动校验每条历史记录。

## 2.1.0：慢速扫描与取消

文件系统枚举使用独立的单工作线程，不再占用本地查询队列。扫描期间可以搜索、翻页、切换布局和查看详情，显示既有数据库记录；暂时禁止修改操作和第二次扫描。枚举完成后的本地数据库事务仍串行执行，该短暂阶段查询可能等待，不承诺扫描全过程零等待。

界面每 250 ms 读取内存进度，显示当前 Bucket、已发现资源数和经过时间，不为进度额外请求 NAS。没有预先遍历以计算总量，因此不展示虚假的百分比。Root 管理、选定 Root 的侧栏显示最近成功扫描时间，并注明状态来自历史扫描，不轮询网络在线状态。

取消是协作式的：在枚举检查点和提交前检查取消请求；取消后不修改资源、标签、待处理项或 Root 的扫描时间。已经发出的系统/SMB 读取可能无法立即中断，界面会显示“等待当前读取返回后取消”，此时仍可查询本地记录。开始数据库事务前锁定提交阶段，按钮随之禁用；之后完整提交或回滚，不强行打断事务。关闭程序也发出取消请求，并在扫描退出后释放数据库。

## 后续开发规范：必须考虑 NAS 使用体验

本工具主要面向 SMB/NAS 资源库。后续功能、插件和性能评估都应考虑网络延迟、短时断线、低吞吐以及共享目录内容被外部修改的场景；功能完整性优先于性能，不能为了快而漏项、误判缺失或丢失标签。

- 元数据、日志和未来缩略图缓存保留在本机；日常浏览优先读本地记录，避免每次重绘逐项访问 NAS。缓存失效策略在具体预览功能落地时确定。
- 后续预览应限制并发，取消不可见项尚未开始的请求；考虑同一内容请求合并、大预览优先、失败后的明确重试入口。当前仅有有限并发及生命周期取消，缓存和请求合并尚未实现。
- 导入按批次读取 Bucket 容量，成功后直接登记。进度从实际复制字节累计，不额外读回整份文件校验；最终放置时避免再次完整复制，具体行为需要验证。保留来源和明确失败结果。
- 不默认引入文件监听、定时全量扫描、自动重试风暴、逐项在线探测或复杂一致性机制。新增远程读取应有明确用途。
- 验证至少覆盖慢读取时本地浏览、断线/权限失败、取消和重试的数据完整性。性能报告区分本地测试、模拟网络阻塞与真实 SMB/NAS，不把本地耗时当成 NAS 保证。

这些规矩是当前工作基线，不是永久限制；发现更简单、更可靠的方案，随时可以同步优化实现、测试和文档。

目前已完成 Bucket 扫描和 NAS 扫描交互优化。拖入复制、自动建 Bucket、容量分配都尚未实现，不能通过拖入期待文件被保存。

文件先复制到专用暂存目录，成功后放入目标 Bucket，再直接登记新资源，不重新扫描整个 Root。保留来源；失败报告结果。先不做断点续传或复杂任务日志，复制完成但未入库的资源由后续手动扫描找回。具体暂存清理与最终放置行为在实现导入时验证。

### 2.1.1：恢复操作与 Bucket 扫描规则一致

重新定位、取消忽略及确认类型变化均先检查父 Bucket，再检查资源本身；父 Bucket 与扫描一样必须是非隐藏、非系统、非链接的有效目录。重新定位或确认类型变化不符合条件时拒绝操作，保留原有记录、标签及待处理项。取消忽略时，被排除或明确消失的 Bucket 下资源进入 Missing，不会错误恢复为 Active；读取异常仍回滚操作。Bucket 恢复正常后可以重新定位、确认或扫描恢复。

这一修复不增加扫描读取次数，只在上述单资源操作中额外检查一次父 Bucket。
